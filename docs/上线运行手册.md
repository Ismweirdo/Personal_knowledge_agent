# 上线运行手册

## 发布前

- 使用随机强 `JWT_SECRET`，配置数据库、Redis 与 DeepSeek 密钥；本地 BGE-M3 Embedding 使用 Compose 内部服务地址及占位 API Key。
- 设置 `APP_ENV=production` 和 `RATE_LIMIT_ENABLED=true`。
- 运行 Alembic 迁移，并配置 `ADMIN_USERNAME`、`ADMIN_PASSWORD` 和 `VISITOR_ACCESS_KEY`。
- 确认 Nginx 将 `/api/` 代理到后端，SSE 路径关闭代理缓冲。
- 只开放 80/443；PostgreSQL、Redis 和 `/metrics` 不对公网开放。
- 确认私人上传目录、`.env`、备份目录不在 Git 仓库中。

## 推荐服务器

当前 Compose 还运行本地 BGE-M3 Embedding 服务，早期仅使用远程 Embedding API 时的 `2 GiB` 内存建议已不适用。已部署服务器的模型缓存约占 `4.3 GiB` 磁盘；规划容量时还需为 PostgreSQL、上传文件、Docker 镜像及模型加载预留空间，并持续观察内存、磁盘和数据库连接数。CPU 推理的首轮模型下载和加载可能明显慢于其他服务启动。

系统建议 Ubuntu 24.04 LTS。公网安全组只开放 SSH、HTTP 和 HTTPS；SSH 使用密钥登录，关闭密码登录。聊天模型走 DeepSeek API；Embedding 由 Docker 内的 FastAPI/FlagEmbedding BGE-M3 服务提供，Ollama 仅作为本地开发回退。

## 首次部署

1. 安装 Docker Engine、Docker Compose Plugin、Git 和 Nginx/Certbot。
2. 拉取仓库代码，复制 `.env.example` 为 `.env`，只在服务器本地填写真实密钥。
3. 将 `APP_ENV=production`、`RATE_LIMIT_ENABLED=true`，并替换 `JWT_SECRET`、`POSTGRES_PASSWORD`、`REDIS_PASSWORD`、`LLM_API_KEY`、`ADMIN_USERNAME`、`ADMIN_PASSWORD` 和 `VISITOR_ACCESS_KEY`。同时让 `DATABASE_URL` 中的密码与 `POSTGRES_PASSWORD` 一致；保留本地 Embedding 服务的 `EMBEDDING_BASE_URL=http://embedding:8001/v1` 与非空占位 `EMBEDDING_API_KEY`。
4. 在仓库根目录执行 `docker compose --env-file .env -f deploy/docker-compose.yml config --quiet`，再执行 `docker compose --env-file .env -f deploy/docker-compose.yml up -d --build`。`env_file` 负责向容器注入变量；Compose 的 `${变量}` 插值需通过 `--env-file` 或运行目录中的 `.env` 提供。
5. 使用 `docker compose --env-file .env -f deploy/docker-compose.yml ps` 确认容器健康。首次启动需等待 BGE-M3 模型下载与加载完成。
6. 配置域名解析到服务器公网 IP，用 Nginx 或云厂商证书服务启用 HTTPS。
7. 访问 `/health` 和 `/health/ready`，完成管理员登录、知识导入、访客问答、评论提交和重启持久化验证。

国内服务器访问 GitHub clone 链路可能较慢。系统会先尝试浅克隆，失败后自动改用 GitHub 仓库压缩包下载并走同一套清洗规则；若公开仓库仍超时，可先在服务器 `/opt/laylight/git-imports` 下手动 clone，再在管理员端填写容器路径 `/app/git-imports/仓库目录名`。

## 验证

1. `/health` 返回 200，`/health/ready` 的数据库和 Redis 均为 up。
2. 访客通过站点密钥进入，普通 USER 访问知识写接口返回 403。
3. 上传、索引、发布、访客 SSE 问答、引用链路和 HR 评论提交可用。
4. 管理员可查看知识库、侧边候选审核和访客评论；图谱展示与复习计划暂不作为上线验收项。
5. 登录、上传和问答超过限额后返回 429 与 `Retry-After`。
6. 容器重启后数据库、上传文件、索引和评论仍存在。

## 备份恢复

每日执行 `deploy/backup-postgres.sh`，默认保留 14 天。上传文件卷需要使用服务器快照或对象存储版本控制另行备份。每月至少在隔离环境执行一次 `restore-postgres.sh`，并验证管理员登录、知识库数量、Chunk 数、问答引用和 `visitor_feedback` 评论记录。

## 故障处理

- 按 requestId 查询结构化请求日志，不记录 Token、Prompt 或文档正文。
- 就绪检查失败时先检查数据库连接、Redis 和迁移版本。
- 模型服务失败时保留旧知识版本，禁止删除现有活动向量后重试。
- 回滚应用镜像时确认其支持当前数据库迁移版本；数据库回滚必须先备份。

### 上传 PDF 返回 Internal server error，日志提示 Redis AUTH

已观察到后端限流中间件在执行 `redis.incr` 时抛出 `AUTH <password> called without any password configured for the default user`。请求在进入 PDF 解析逻辑前已失败，不能据此判断 PDF 文件或 PyMuPDF 有问题。原因是后端通过 `../.env` 取得非空 `REDIS_PASSWORD`，而旧版 Compose 在 `deploy` 目录运行时用 `${REDIS_PASSWORD:-}` 插值为 Redis 容器显式设置了空值，覆盖 `env_file` 注入的密码；重建旧配置的容器仍会复现。修复提交 `d794b80` 移除了该覆盖，同时让 PostgreSQL 和后端读取同一份根目录 `.env`。

服务器的 `deploy/docker-compose.yml` 若有手动修改，先在仓库根目录查看 `git diff -- deploy/docker-compose.yml`，执行 `git stash push -m "server compose changes before update" -- deploy/docker-compose.yml`，再 `git pull --ff-only origin main`。拉取后不要直接 `git stash pop`，应先核对远程文件是否已包含所需修改。在 `deploy` 目录执行：

```bash
docker compose --env-file ../.env config --quiet
docker compose --env-file ../.env up -d --force-recreate redis
docker compose --env-file ../.env exec -T redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli ping'
docker compose --env-file ../.env up -d --force-recreate backend
docker compose --env-file ../.env ps
```

Redis 命令应返回 `PONG`。随后查看 `/health/ready` 响应体中的 `redis` 是否为 `up`，实际重新上传 PDF，并检查新产生的 backend 日志。容器 `healthy` 或 `/health/ready` 返回 HTTP 200 本身不足以证明限流和上传请求可用。2026-09-15，服务器使用者确认 Redis 验证和 PDF 上传均已成功，此故障的实际使用链路已恢复。此后已取得服务器只读检索评测与公网问答小样本结果，见 [验证与评测说明](验证与评测说明.md)。如果数据库使用已有持久卷，修改 `.env` 的 `POSTGRES_PASSWORD` 不会自动修改卷内数据库密码，后端 `DATABASE_URL` 必须与现存数据库密码一致。

本次公网 `/health/ready` 虽为 200，但响应 `checks={}`，没有返回数据库/Redis 探针结果；服务器使用者随后在 backend 容器核实 `APP_ENV=development`，与代码在非 production 模式下不装配探针一致。因此当前站点虽可问答、可检索、可上传 PDF，尚不能宣称生产环境就绪检查通过。切换前先在服务器本地核对 `JWT_SECRET` 是否已换成长随机值、`LLM_API_KEY` 是否非空、`RATE_LIMIT_ENABLED=true`、Embedding 模型及占位 API Key 是否配置，并检查数据库/Redis 密码；生产模式的配置校验会拒绝缺少这些项的启动。不要在聊天或日志中打印完整 `.env`、密钥或包含密钥的 `docker compose config` 输出。完成安全配置后再设置 `APP_ENV=production`、重建 backend，确认 `/health/ready` 返回 `database=up`、`redis=up`，再复测访客登录、PDF 上传和问答。

日常后台操作见 [管理员使用说明](管理员使用说明.md)。已知故障模式和历史解决过程见 [开发文档](开发文档.md)。生产出现新故障时，恢复服务后必须补充现象、根因、处置、验证和预防措施。
