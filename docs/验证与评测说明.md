## 检索评测

`evaluation/datasets/project_baseline.jsonl` 仅包含公开项目知识和不可回答问题，不包含私人简历事实。它的 `expected_terms` 只能衡量检索文本是否覆盖关键词，没有正确来源标注，因此脚本会将 `recall_at_k` 输出为 `null`。有人工标注的来源评测使用 `evaluation/datasets/public_source_gold.jsonl`：12 道可回答题各标注一个主要正确文档，另有 2 道不可回答题。先完成向量索引，再运行：

```bash
cd backend
python scripts/evaluate_retrieval.py \
  --published \
  --dataset evaluation/datasets/public_source_gold.jsonl \
  --top-k 1 4 10
```

脚本只读取已发布知识库、活动来源和 Chunk，调用真实 Embedding，不写入知识内容；输出活动来源/Chunk 数、每个 K 的文档 `recall_at_k`、可回答关键词覆盖率、不可回答空检索率和总体成功率。`recall_at_k` 按每题被检索到的标注来源占全部标注来源的比例求平均；它是文档级 Recall@K，不是相关 Chunk 或最终回答的正确率。若没有 `gold_source_names`，`recall_at_k=null`。单元测试中的 100% 是 Fake Retriever 的框架自测，不能用于上线结论。

为避免手工导入遗漏，可在空的隔离 PostgreSQL/pgvector 数据库中导入六份公开项目文档、调用真实 BGE-M3，并使用相同标注集评测多个 K：

```bash
cd backend
DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:55432/knowledge_agent_eval \
python scripts/run_public_source_recall.py --top-k 1 4 10
```

脚本会向目标数据库写入评测用户与六份公开文档，只能对空的隔离评测库运行，不读取私人简历。`scripts/run_project_baseline.py` 仍可评测 Git 清洗后的整体快照，但它没有来源标注，不能输出文档 Recall@K。在 Windows PowerShell 中请先用 `$env:DATABASE_URL='...'` 设置评测库连接，再执行脚本。

2026-09-15，本地 FastAPI/FlagEmbedding BGE-M3 与 PostgreSQL/pgvector 的隔离复测使用六份公开文档、23 个 Chunk、12 道标注来源的可回答题和 2 道不可回答题：

```json
{
  "top_k_reports": {
    "1": {"recall_at_k": 0.75, "answerable_hit_rate": 0.9167, "unanswerable_empty_rate": 0.0},
    "4": {"recall_at_k": 1.0, "answerable_hit_rate": 1.0, "unanswerable_empty_rate": 0.0},
    "10": {"recall_at_k": 1.0, "answerable_hit_rate": 1.0, "unanswerable_empty_rate": 0.0}
  }
}
```

指标定义如下：

| 指标 | 计算 | 当前判定 |
| --- | --- | --- |
| 文档 Recall@K | 可回答题的 Top K 命中人工标注的主要正确文档；本集每题标注 1 个来源 | K=1：9/12=75%；K=4/10：12/12=100% |
| 可回答关键词覆盖率 | Top K 合并文本包含该题全部 `expected_terms` 的比例；不等于相关 Chunk Recall | K=1：11/12=91.7%；K=4/10：12/12=100% |
| 不可回答空检索率 | 不可回答题返回空片段的比例；不等于最终拒答正确率 | K=1/4/10 均为 0/2 |
| 总体成功率 | 上述可回答关键词覆盖与不可回答空检索合并，分母为全部 14 题 | K=1：11/14=78.6%；K=4/10：12/14=85.7% |

2026-09-14 的旧整体快照测试（96 文件、19 Chunk、12 题）把 12 题总体成功率 `33.3%/66.7%/66.7%` 错命名为 Recall@1/4/10；同次测试 10 道可回答题的关键词覆盖率实际为 `40%/80%/80%`，没有文档标注，不能补算 Recall。2026-09-15 的新整体快照复测已变化为 110 文件、13 Chunk；其可回答关键词覆盖率为 `40%/50%/70%`（K=1/4/10），`recall_at_k=null`。不同快照不能直接当作模型效果升降对照。

当前实现没有相似度拒答阈值，未知问题仍检索到低分 Chunk。空检索率和固定无证据拒答因此都可能偏低，必须分别报告最终回答是否确实拒绝了无依据预测。

### 已部署站点的真实问答与引用测试

2026-09-15 从 Windows 客户端通过 `https://laylight.asia` 发起 SSE 请求，管理员只读来源列表显示已发布知识库有 22 个 READY 文件来源（21 份 Markdown、1 份 PDF）、50 个活动 Chunk。服务器随后用同一标注集直接运行只读 `evaluate_retrieval.py --published --top-k 1 4 10`：12 道可回答题的文档 Recall@1/4/10 分别为 9/12=75%、11/12=91.7%、12/12=100%；检索文本的关键词覆盖分别为 11/12=91.7%、12/12=100%、12/12=100%，两道不可回答题在三个 K 下的空检索率均为 0/2。当前只标注了每题一个主要正确文档，文档 Recall@10=100% 不代表正确段落或最终答案均命中。

同一题集的线上问答 14/14 请求收到 `done`；12 道可回答题的首条引用命中标注文档为 9/12，Top 4 引用命中标注文档为 11/12，最终回答包含全部预期关键词为 10/12。两道漏答分别是会话/通用检索的 Top K 和 Git 克隆的免交互配置：第一道未引用标注文档，第二道虽引用了 `开发文档.md`，却没有取到含所需配置的段落。这说明来源命中不等于正确 Chunk 或正确回答。

两道不可回答题均返回非空引用，固定无证据拒答为 0/2；人工检查最终文本，天气和股价两题都明确拒绝预测（2/2），但回答附带了无关项目介绍。该样本量过小，不能宣称系统总体拒答正确率。线上 SSE Top 1/4 数字与服务器直接执行的 `limit=1/4` 来源召回结果一致；`limit=10` 已完成单独评测。服务器 backend 当前 `APP_ENV=development`，公网 `/health/ready` 的 `checks={}`，因此这些实测指标只证明现有部署链路可请求、可评测，不是生产配置与依赖探针验收。切换 production 前置条件见 [上线运行手册](上线运行手册.md)。

### 当前 RAG 参数与拒答边界

本项目当前没有通过离线评测选出的“最优 Token 参数”，以下是已实现、可从代码复核的运行值，不能表述为效果调优结论。

| 项目 | 当前实现 | 说明 |
| --- | --- | --- |
| Chunk 大小 | 2400 字符 | `chunk_pages` 优先按段落聚合；超长段落再按窗口切分。`token_count` 是 `字符数 / 4` 的近似记录，不是模型 tokenizer 的精确 Token 数。 |
| Chunk 重叠 | 300 字符 | 约为窗口的 12.5%，只在相邻 Chunk 之间保留尾部文本。 |
| 问答 Top K | 4 | 会话服务调用检索时固定 `limit=4`，最多将 4 条证据写入上下文。 |
| 通用检索默认 Top K | 10 | `RetrievalService.search` 的默认值；离线脚本的 `--top-k` 默认也是 10，可显式改写用于对比。向量查询每个扩展 Query 先取 `max(3K, 12)` 个候选，再做来源均衡。 |
| 拒答阈值 | 未配置数值阈值 | 当前仅在“检索结果为空”时确定性拒答；没有相似度分数 cut-off。低分但非空结果仍会进入 Prompt，因此分数阈值是待评测后实现的优化项。 |

### 本地 Embedding 迁移（FastAPI + FlagEmbedding/BGE-M3，Ollama 回退）

2026-09-14 已将主路径适配为独立 FastAPI 服务：Docker Compose 的 `embedding` 服务使用 `BAAI/bge-m3`/FlagEmbedding，暴露 OpenAI 兼容的 `http://embedding:8001/v1/embeddings`。模型使用 1024 维输出。Ollama `bge-m3` 保留为开发或服务故障回退。迁移 `20260914_01` 会清空旧向量、将来源版本标记为待索引；这是必要操作，因为不同模型或实现生成的向量不能混合检索。

```bash
# Compose 会构建 FastAPI/FlagEmbedding 服务并在首次启动下载模型
cd deploy
docker compose up --build

# 项目：执行数据库迁移并重建已有 Chunk 向量
cd backend
alembic upgrade head
python scripts/reindex_embeddings.py
python scripts/run_project_baseline.py --top-k 1 4 10
```

主路径以 OpenAI 兼容接口返回 BGE-M3 的 1024 维、L2 归一化 dense 向量；它不需要第三方 API Key。实际验证确认该接口可返回 2 条、各 1024 维向量；后端对该本地端点使用 `EMBEDDING_BATCH_SIZE=4` 与 `EMBEDDING_REQUEST_TIMEOUT_SECONDS=300`，避免把云端默认批量/超时误用于 CPU 推理。Ollama 回退已在宿主机真实返回 1 条 1024 维向量；若需从 Compose 容器访问它，Ollama 必须额外监听非回环地址，`host.docker.internal:11434` 才可连通。

模型首次下载的端点由 `HF_ENDPOINT` 控制，Compose 默认使用 `https://hf-mirror.com`；在可直接访问 Hugging Face 的环境可显式设置为 `https://huggingface.co`。若两者都不可达，应先处理服务器出网或通过离线方式预置模型缓存，而不是反复重启容器。

服务会先以 `snapshot_download` 下载推理所需模型文件，并忽略仓库中的示例图片目录 `imgs/*`；这样可避免镜像站拒绝非推理资源（例如 `.DS_Store`）时阻断整个模型启动。

Compose 同时设置 `HF_HUB_DISABLE_XET=1`，避免受限网络通过 Hugging Face Xet/CAS 通道下载权重时出现 401；模型权重会回退为普通 HTTP 下载。

### 访客问答耗时的测量口径与本次结果

旧的“首批文字约 1.24 秒、总耗时约 2.78 秒”仅是一次成功链路的体验采样，不是 P50/P95。2026-09-15 使用 `scripts/measure_live_chat.py` 经公网 HTTPS 对真实 `messages:stream` 事件计时；每组只统计收到 `done` 的成功请求，失败与超时单列。采样客户端位于 Windows 网络环境，包含客户端至 Nginx 的往返、后端检索和 DeepSeek 流式生成，不等于服务器内部模型耗时或生产 SLA。

- 起点 `t0`：浏览器发起 `POST /api/v1/conversations/{id}/messages:stream` 的时刻（Network 面板请求开始）。
- 首字/首批文字 `TTFT`：收到首个非空 `event: delta` 的时刻减 `t0`；不把 `metadata`、`citation` 等非回答事件算作首字。
- 总耗时：收到 `event: done` 的时刻减 `t0`；若收到 `event: error`，单独记录失败，不混入成功样本。
- 原始本地 JSON 保留每题的事件计时、引用来源与回答，未提交到仓库；报告记录样本数、问题类别、并发度和是否拒答，以便区分网络波动与模型负载。

| 真实请求组 | 成功数 | 首字 P50 / P95 / P99 | 总耗时 P50 / P95 / P99 | 口径 |
| --- | ---: | --- | --- | --- |
| 14 道混合标注题，每题一次 | 14/14 | 1.563 / 1.992 / 2.128 秒 | 2.174 / 2.758 / 2.791 秒 | 问题各异；包含 12 道可回答与 2 道不可回答。 |
| 同一个“你做过哪些项目？”问题，串行 10 次 | 10/10 | 1.189 / 16.766 / 16.766 秒 | 3.025 / 17.692 / 17.692 秒 | 有一次明显慢请求；10 样本的 P95/P99 都落在最大值。 |
| 同问题 6 次，并发度 2 | 6/6 | 未单列 | 5.504 / 13.071 / 13.071 秒 | 客户端完成吞吐 0.277 请求/秒；仅是小样本探索。 |

串行采样中 9/10 的首字低于 2.2 秒，剩余一次约 16.8 秒；并发组也有约 13.1 秒的慢请求。只展示中位数会掩盖实际长尾，需在更长、更稳定的采样窗口复测后才能建立容量或 SLA 结论。

## 并发基线

```bash
cd backend
python scripts/load_test.py --base-url http://localhost:8080 --requests 200 --concurrency 20
```

`load_test.py` 只请求 `/health`，其吞吐和 P95/P99 不能作为聊天或 Embedding 的性能数字。本次真实 SSE 小样本由 `scripts/measure_live_chat.py` 采集；它会通过环境变量读取测试访客密钥，测试结束后仅删除自身创建的三个对话，不输出密钥或 PDF 正文。若要取得容量上限，应在服务器或独占 runner 上分时段进行更多真实聊天请求，同时监控 CPU、内存、数据库连接、Embedding 排队和错误日志。
